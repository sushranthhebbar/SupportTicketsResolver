Section 6

Implementation

6.1 How it was built

The repository was created on 26 October 2026. The first week went on the discovery workbook, the requirements, the prompt library and the sprint plan. In the second week I built the normaliser, the evaluation harness, the classifier and router, retrieval, grounded drafting with its guardrails, the escalation summary, the agent review page, outcome capture and the dashboard. The third week is for governance, this report and the video. The code has one module per job (tickets, classification, routing, retrieve, answering, guardrails, escalation, pipeline, evaluation and the stores), so each can be tested alone. The tests run with python -m pytest tests -v; 62 of them run under Python 3.9 and pass, and two files, for the review API and the dashboard, need Python 3.11.

The evaluation harness takes an input path and an output path as arguments, because the final assessment runs it on a file I have not seen. A failing ticket is recorded as an error and the run continues. The harness writes one result row per ticket, builds a metrics report, and can resume an interrupted run by reusing the tickets already done. The resume feature turned out to be essential.

6.2 What was hard

The model provider. My first full run, on 1 November, finished 6 of 80 tickets before the free provider began answering HTTP 429, "too many requests". After moving to Groq on 2 November the first attempt reached 18 tickets. I added pacing between requests, retries that wait for the reset time the provider states, and the resumable run. The final validation run still took two sessions on two days because of the daily token allowance, so the criterion of a single unattended run is not strictly met on the free tier.

Citations. My first drafting prompt let the structured citation list and the inline identifiers disagree, which would have thrown away sound drafts. Version 2 of the prompt (3 November) requires them to match, and the stored citations are taken only from the inline identifiers, each checked against the passages retrieved for that ticket. A small probe on development tickets showed the failure that remains: a draft can cite a real document that does not back its sentence, and the check cannot see that. For that reason I call it a retrieval check.

Evaluation method. The hardest problem was not a bug. My first calibration split was by text hash, and nearly every held-out ticket had a paraphrase in the fitting set. I replaced it with a split by scenario, grouping near-duplicates by shared content words (about 79 groups in the development set). The same clustering showed that intervals computed on single tickets were far too narrow, so every interval in this report resamples whole scenarios. Separately, 67 of 97 groups of identical ticket text carry different urgency labels. I report that conflict and did not relabel, because the hidden set may conflict in the same way.

Smaller problems. The vector store printed telemetry errors and reloaded the embedding model for every ticket, which I fixed by pinning a dependency and loading once. The pipeline reported its latency as empty, so the first report had no latency figures; I changed the report to use the harness's own timing and added a test. A malformed ticket in an input file stopped the whole run, which I found while testing failure handling (Section 8.5) and fixed.

6.3 What I would change

I would add a live intake, so that the fallback which sends a ticket to review when classification fails is something a real queue uses; at the moment only the tests and a demonstration call it. I would have the pipeline record where each ticket's time goes, waiting and retrieval and each model call, which it does not do now. I would keep the prompts together with their versions in one place instead of partly inside the code. And I would build the two draft fixes described in Section 9, which need a fresh, unseen set of tickets to evaluate because the validation set has been used.
