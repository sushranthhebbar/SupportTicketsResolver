Section 5

Architecture and design

5.1 How a ticket moves through the system

A ticket from any of the four channels is first turned into one common format. Customer fields are held apart, and the evaluation labels and historical outcomes are kept out of everything the model sees. A language model then classifies the ticket: one of 22 intents, an urgency, a confidence for each, and for urgency a short quotation from the ticket as evidence. A fixed router decides what happens next. If the intent is a security incident, compliance request, feature request or unclear request, the ticket goes to a specialist, and the system retrieves the closest articles and prepares an escalation summary. Every other ticket gets its five closest passages retrieved, then a draft written by the model from those passages only, then guardrail checks on the ticket and the draft. What comes out is either a draft waiting for an agent, or a note to a human saying why no draft was possible. Each step adds a row to the decision log. Figure 2 shows this path.

Retrieval covers the 29 supplied articles. Each is cut into passages of about 800 characters with a 120-character overlap, embedded with the MiniLM sentence model and kept in a persistent vector index. The drafting prompt tells the model that ticket text is untrusted data, allows it to use only the retrieved passages, and requires an inline citation such as [DOC-AUTH-004] after each claim. Agents work in a small web page where they can read a draft and its sources, edit it, approve it, reject it or escalate it, and approval runs the citation and safety checks again. A separate store holds observed outcomes and agent feedback, and a dashboard summarises decisions, guardrail activations and outcomes by customer tier and fluency, with a plain statement that it makes no causal claim. The language model was Qwen 3.8 27B served by Groq on its free tier. The classification prompt is PR-03 and the drafting prompt is PR-02; Table A1 in Appendix A lists every prompt and its versions.

5.2 Choices and alternatives

Table 4 sets out the main design choices, the alternative considered for each, and the reason for the choice.

5.3 What it does not have

There is no live intake. Tickets enter through the evaluation runner, the scripts and the tests, and nothing reads a real support inbox. The system does not measure agent time and does not detect duplicate tickets, although the data has many near-duplicates (Section 9). It depends on a single model provider, and I tested what happens when that provider fails (Section 8.5) without removing the dependency.
