Section 8

Governance and risk

The governance framework offers one test: pick a way the system could harm a customer and ask what in the design stops it. Where my answer was only a property of the model, I have said so and not counted it as a control. The full governance document is docs/governance.md in the repository.

8.1 Decision logging

Every ticket writes a classification row and a routing row, plus either a drafting row or an escalation-summary row, and agent actions add a review row. The log holds every field in the framework's minimum record. On the final validation run it reconciles exactly: 80 tickets, 80 classification rows, 80 routing rows, 63 drafting rows and 17 escalation rows, so every ticket has a draft or a summary and none has both. Three weaknesses remain. The list of alternatives is never filled, because the classifier returns one label. The drafting row stores the full ticket text and passages so that the review page can show them, which means access to the database needs a retention rule that CloudServe has not set. And before my coverage check a classifier failure left no row at all; it now writes an error row.

8.4 Guardrails and the demonstration

The framework names five guardrails. The confidence floor is in place: a missing or out-of-range score goes to review. Private data and instruction integrity are partly covered, since they scan the ticket and the draft for credential-like strings and phrases such as "ignore the previous instructions" and nothing more. Grounding is partly covered: it requires an inline citation to a retrieved document and does not test the claim. Tone and scope, which should stop the system promising a refund or a deadline, is not built. When a guardrail fires, the draft is blocked, the ticket goes to review and the block is logged.

The validation run produced no block, so I tried to provoke one. Seven tickets built to make the model repeat a credential or write an injected sentence all failed, because the model refused or pointed out the credential. That is good behaviour, but it belongs to the model and not to a control I wrote, so it does not satisfy criterion A7. I added a check on the ticket itself. If the subject or body contains a credential-like or instruction-like string, the pipeline skips drafting, writes a block decision naming the category and not the secret, and routes the ticket to review. Four engineered tickets sent live through the real pipeline and model were all blocked, with a logged block and no draft. The same patterns match none of the 580 development and validation tickets, so the check would not have changed an earlier result, although the validation run predates it.

8.5 Failure handling

I induced each failure the specification names. With the provider's address pointed at a closed port, a two-ticket run finished and logged both errors; a disconnection during drafting produced a note for a human to retry later. A rejected key, a timeout and rate limiting (the last two simulated, with retries) gave the same safe result. An empty retrieval and a retrieval crash each produced a note for review. One malformed ticket in a file of three stopped the whole run, which was a defect; the harness now skips invalid records, lists them and processes the rest. When classification is unavailable, an option sends the ticket to review with no intent and writes a routing row, so the log still reconciles. Nothing in the prototype uses that option yet, since there is no live intake.

The kill switch is the weakest part of the design. There is no dedicated switch. The system cannot send to a customer, and automatic routing is off whenever the calibration setting is unset, but turning anything off means editing the environment file and restarting the service. That takes about a minute, applies from the next start and not the next ticket, and is open to anyone who can edit the file. I have not tested restart-to-stop as a switch. Before any real deployment I would add a flag read on every ticket, with a named operator.

Declaration, in the framework's words This system must never send a message to a customer without an agent approving it, or answer a security incident, compliance request, feature request or unclear request without a specialist. What enforces that: the code has no send path, approval is a separate agent action that runs the citation and safety checks again, and a routing rule escalates those four intents whatever the confidence (14 of 14 on validation, 64 of 64 on development). The most likely way it could still do harm: a fluent, cited draft that gets one claim wrong or applies an article to the wrong plan, which a busy agent approves. We would not deploy it without: a two-assessor review of at least 50 drafts, a supervised pilot, the plan-scope and commitments checks, a tested runtime kill switch, and agreed rules for data access and retention.
